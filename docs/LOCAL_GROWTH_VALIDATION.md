# 加密 F2FS 局部搬移验证

日期：2026-10-20。首轮实验限定 V50 Pro 的 `v50-hyperos4-r1`，当时保留 Alpha 9 的正式原生资产；使用 `build.py --local-growth` 编译独立候选。后续 Alpha 11 的随包资产已启用该构建开关，首轮计时及启动覆盖范围仍按下文分别记录。

## 原理与改动

Alpha 9 为避免普通 F2FS 整理错误地通过元数据解密视图搬移 fscrypt 文件密文，禁用了原生局部整理分支，改为全 Main 区迁移。每个数据块搬移还会更新节点，因而产生大量 4 KiB I/O。

实验构建同时补丁化 `resize.c` 与 `defrag.c`：先获取源 SSA 摘要；加密普通文件的数据块通过原始密文映射直接复制，节点、目录与其他元数据通过解密映射搬移；随后沿用上游 SIT / SSA / NAT / 节点指针及检查点更新。保留对齐直接 I/O、挂载回放、文件系统检查及 FBE 密封记录一致性验证，不忽略错误。

局部整理成功时，大部分文件保持原物理位置；整理失败仍保留原有全迁移回退路径。没有修改槽位密钥封装、加密算法或用户密码。

## 独立副本实测

使用原 16 GiB 完整备份，在独立 `IImageService` 命名空间创建 18 GiB 候选。该命名空间不位于 DSU 槽注册目录；镜像名称与真实 `userdata_gsi` 不同。原始备份始终保留，复制与独立读回均按原备份 SHA-256 核对。

普通加密文件和不继承文件加密的文件经 loop 映射均未通过原生几何预检，没有进入扩容。最终采用与真实 DSU 相同的 gsid / Fiemap 原始映射后通过；没有把 loop 测试环境的失败归为算法数据损坏。

| 本机单次测量 | 耗时 |
| --- | ---: |
| 原全量搬移文件系统阶段 | 约 47–48 分钟 |
| 独立候选复制、尾部清零及校验 | 35.52 秒 |
| 新文件系统阶段：预检、回放、局部搬移、检查及密封记录复核 | 43.27 秒 |
| 仪器测试整体，含候选最终全量摘要 | 97.68 秒 |

新路径返回 `Try to do defragement: Done`；块设备与文件系统均为 19,327,352,832 字节，12 份 FBE 密封记录检查通过。上述约 66 倍改善仅指这一次设备和布局的文件系统阶段，不代表整项应用事务或其他设备也有同样倍数；原应用的完整备份、恢复和校验仍会发生。

## 冷启动验收状态

当前 18 GiB 正式状态已另存完整恢复点并独立校验；候选写入授权槽后再次全量校验，过程中有持久化实验记录与启动阻止标记。原有 Alpha 9 的 16 GiB 备份和增长记录未删除。

快速候选完成一次真实冷启动，用户解锁成功。64 MiB CE 文件、其硬链接与 8 MiB DE 文件的 SHA-256 均与原 16 GiB 基线一致；inode、链接数、0600 权限、属主 / 属组及 fscrypt 加密标记均一致。锁屏阶段的 DE 校验也通过，四份原槽元数据密钥封装记录的摘要保持不变。

另在 CE 测试目录完整写入并同步 5.25 GiB 随机文件，耗时约 13.08 秒；两次独立读取的 SHA-256 一致。客体总已用空间达到约 16.63 GiB，超过原 16 GiB 上限，确认新增容量可实际使用。本次未对新增文件执行第二次客体冷启动；上一轮 Alpha 9 全迁移路径的两次启动结果不能当作局部搬移路径的第二次启动结果。

验收后已返回主系统，使用测试前完整 18 GiB 恢复点恢复真实槽，写回后的整盘 SHA-256 与恢复点一致，实验记录进入 `RESTORED`。主系统硬件 Keystore 解封装与真实槽只读预检再次通过，四份原槽密钥封装记录和六个 system / system_ext / product 顶层镜像文件统计与基线一致。启动选择、单次标记和 DSU 停用状态已恢复。

独立候选通过 `IImageService.deleteBackingImage` 删除并确认注册不存在；未映射的 loop 试验文件、额外 18 GiB 恢复点、原生助手、临时文件与设备测试包已清理。正式 Alpha 9 的 16 GiB 回退备份与加密协作凭据继续保留。

该实验使用只接受独立候选映射名称的专用原生入口，未放宽正式应用的 `userdata_gsi` 校验，也未把任意映射入口或测试凭据写进普通 APK。构建与验收输出仅保留在本地忽略目录；设备上的实验资产已清理，不提交密钥、设备文件或本机配置。

首轮仅验证单个设备、单个增长布局，未覆盖断电、空间耗尽、局部整理失败后的全迁移回退或硬件封装密钥。当时未切换普通 APK 的维护资产；单独重编原生脚本仍需显式添加 `--local-growth`。Alpha 11 的后续集成及更大候选验证见下节。

## Alpha 11：16→128 GiB 独立候选与集成

同日用户要求停止 V50 上仍由 Alpha 9 执行的 16→128 GiB 全量迁移，并更新应用。匹配进程身份后只向 resizer 发送 SIGTERM，事务正常保存 `RECOVERY_REQUIRED`；随后使用真实硬件协作凭据回退，原始备份及回写数据的完整 SHA-256 校验通过，文件系统预检通过，实际槽回到 16 GiB / `ROLLED_BACK`。原始 16 GiB 备份与协作凭据保留。

在独立 gsid / Fiemap 命名空间复制本次备份，创建 128 GiB 候选并清零扩展区域；实际槽保持回退后的状态。初次助手沿用 180 秒测试限时，导致独立候选整理被中止，随后清理临时映射、重置副本并以 600 秒限时重新验证。该失败没有操作真实槽，不能计为通过的扩容。

| 本次 16→128 GiB 独立候选 | 耗时 |
| --- | ---: |
| 原始复制、读回校验及 112 GiB 尾部清零 | 121.19 秒 |
| 文件系统阶段，含预检、回放、局部整理、检查和密封记录复核 | 519.19 秒（约 8 分 39 秒） |
| 仪器测试整体 | 641.85 秒 |

局部整理返回 `Done`，扫描范围 406,847,488 字节（388 MiB）；文件系统和块设备均为 137,438,953,472 字节，12 份 FBE 密封记录检查通过。该范围是当前整理区域，不能当作整个事务的数据处理量或物理闪存写入量。目标布局与首轮 18 GiB 候选不同，不能将首轮 43 秒外推至 128 GiB。

128 GiB 候选未执行客体冷启动或用户 CE 文件验收；此前 18 GiB 候选的启动结果仍按前一节独立记录。本次候选验证后经 IImageService 删除，私有映射、助手、测试包和临时文件已清理。真实槽仍为已校验回退后的 16 GiB，没有自动重试扩容。

Alpha 11 / code 22 的随包工具已启用局部整理并覆盖安装到 V50。整理与全量扫描上报实际逻辑区域进度，元数据维护上报固定阶段名称；Java 层仅转发严格校验的数字协议。安装后的真实硬件凭据解封装和 16 GiB 文件系统预检再次通过。Alpha 9/10 的历史安装包不变，单独重编原生工具仍需显式添加 `--local-growth`。
